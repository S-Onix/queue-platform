# Tenant 통합 가이드

> **대상**: Queue Platform을 자기 서비스에 붙이는 Tenant 개발자
> **정본**: API 필드·에러 코드의 정본은 [`API.md`](API.md)다 — **코드에서 추출한 것**이라
> 구현과 어긋나지 않는다. [`FRS_final.md`](FRS_final.md)는 설계 시점의 **요구사항 원본**이며
> 필드 명세로는 쓰지 마라(둘이 갈리면 코드에서 뽑은 `API.md`가 맞다).
> 이 문서는 **순서와 계약**을 다룬다.
> **최신화**: 2026-08-25 (구현 대조 — 아래 서술은 전부 `queue-api` 코드에서 확인했다)

## 0. 한 장 요약

```
[브라우저]                [Tenant 서버]              [Queue Platform]
    │                          │                            │
    │  1. 상품 페이지 요청      │                            │
    ├─────────────────────────>│                            │
    │                          │  2. POST /tokens (enqueue) │
    │                          ├───────────────────────────>│
    │                          │<───────────────────────────┤
    │                          │     tokenId, seq, rank     │
    │  3. 대기 페이지 + 🔴 tokenId·seq                       │
    │<─────────────────────────┤                            │
    │                                                       │
    │  4. GET /status  (전광판 — 전원 동일, 인증 없음)        │
    ├──────────────────────────────────────────────────────>│
    │  5. GET /tokens/{tokenId}?seq= (차례 임박 시에만)      │
    ├──────────────────────────────────────────────────────>│
    │<──────────────────────────────────────────────────────┤
    │              ready=true, admitToken                    │
    │                          │                            │
    │                          │  6. POST /admit  (내가 받을 수 있는 만큼)
    │                          ├───────────────────────────>│
    │                          │  7. POST /verify 또는 /complete
    │                          ├───────────────────────────>│
```

**Platform은 순서만 관리한다.** 몇 명을 언제 들여보낼지는 **Tenant가 정한다**(6번 `admit`).
Platform이 알아서 밀어 넣는 일은 없다.

## 1. 준비

| 항목 | 얻는 곳 |
|---|---|
| `X-API-Key` | 회원가입 → API Key 발급. **Tenant 서버에만 둔다. 브라우저로 내리지 마라** |
| `queueId` | 큐 생성 시 발급 |

`X-API-Key`가 필요한 것은 **`enqueue`·`admit`·`verify`·`complete` 넷**이다.
브라우저가 부르는 **`/status`와 폴링 둘은 인증이 없다**(§79).

## 2. Enqueue — 줄을 세운다 (Tenant 서버)

```bash
curl -X POST https://<platform>/api/v1/queues/{queueId}/tokens \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"identifier": "0192f3c1-8b2e-7a44-9c31-000000000001"}'
```

```json
{ "isSuccess": true,
  "data": { "queueId":"q1", "identifier":"0192f3c1-...", "tokenId":"tk_...",
            "seq": 1042, "rank": 37, "total": 1042, "already": false } }
```

### `identifier`는 **UUIDv7을 재사용**한다

Tenant가 정하는 자유 문자열(최대 100자)이지만 규칙이 둘 있다.

- **같은 사용자·같은 큐에는 항상 같은 값**을 써라. 새 값을 주면 **줄을 새로 선다**(맨 뒤).
  사용자가 새로고침해도 같은 `identifier`면 `already: true`로 **자리가 유지된다**.
- **추측 가능한 값을 쓰지 마라**(이메일·회원번호·순번). 남의 자리를 점유할 수 있다.

`already: true`는 **오류가 아니다.** 이미 줄을 서 있다는 뜻이고, 응답의 `tokenId`·`seq`는
처음 발급된 그 값이다. 그대로 쓰면 된다.

### 🔴 `already: true`인데 `rank: -1`이면 **줄이 아니라 입장 단계다**

`rank`는 1부터 시작한다. **-1은 순번이 아니라 상태**다 — "이미 `tokenId`를 받았고, 지금
대기줄에는 없다"는 뜻이고, 실제로는 **입장권이 이미 나갔다**는 신호다.

왜 생기나: `admit`은 그 사람을 대기줄에서 빼지만 **중복 방지 기록은 남긴다**(그래야 재진입이
새 줄로 안 센다 = 중복 과금이 안 생긴다). 그 사이에 같은 `identifier`로 `enqueue`가 오면
"이미 있음, 단 줄에는 없음" = `already: true` + `rank: -1`이다. 흔한 계기는 셋이다.

1. 입장권이 나간 직후 사용자가 **새로고침**했다
2. Tenant 서버가 `admit` 응답을 받았지만 **사용자에게 전달하지 못해** 재시도했다
3. 입장권이 **막 만료됐고** 정리가 아직 안 끝났다 (10초 이내)

**무엇을 할 것인가 — 새 줄을 세우지 마라.** 응답의 `tokenId`로 **대기 페이지를 그대로 열면
된다.** 1·2번이면 **첫 폴링이 곧바로 `ready: true` + `admitToken`을 준다**(폴링은 대기줄에
없으면 입장권 발급 기록을 한 번 더 본다). 3번이면 폴링이 **404 `TK001`**을 주는데, 그건 재시도
신호가 아니라 **종료 신호**다 — 그때 같은 `identifier`로 `enqueue`를 다시 부르면 정리가 끝나
있어 **신규로 맨 뒤**에 선다.

**완료 뒤에는 이 응답이 나오지 않는다.** `verify`든 `complete`든 완료가 확정되면 그 회차는 끝이고,
같은 `identifier`의 다음 `enqueue`는 **신규(맨 뒤, 과금 +1)**다 — 어느 엔드포인트로 완료했는지와
무관하게 같다(§92). 완료한 사용자가 새로고침으로 "자리를 되찾는" 일은 없다.

🪤 **`rank`를 그대로 화면에 쓰지 마라.** -1을 거르지 않으면 "-1번째"가 뜬다.
🪤 **정원이 차 있어도 이 응답은 그대로 나온다.** 정원(`maxCapacity`)은 **신규 진입자만** 막는다 —
이미 받은 사람은 정원과 무관하게 `already: true`다.

## 3. 🔴 대기 페이지를 서빙할 때 `tokenId`와 `seq`를 함께 내려보내라

브라우저는 폴링할 때 두 값이 **둘 다** 필요하다. `FRS_final.md`의 흐름 요약(§2·§12)에 한 줄로
적혀 있지만 **왜 필요한지·잃으면 어떻게 되는지가 없어서** 실제로 자주 빠진다. 여기서 못박는다.

```html
<script>
  window.QUEUE = {
    queueId: "{{queueId}}",
    tokenId: "{{tokenId}}",   // enqueue 응답
    seq:     {{seq}}          // enqueue 응답 — 문자열 말고 숫자
  };
</script>
```

**`seq`를 뺄 수 없다.** 폴링 엔드포인트가 `?seq=`를 요구하고, 서버는 이 값으로 대기 항목을 찾은 뒤
`tokenId`로 소유권을 대조한다. `seq`만으로 판정하면 `seq`가 큐별 연번이라 추측이 자명해서
남의 대기 항목을 건드릴 수 있다.

두 값을 어디에 담든(HTML 인라인·쿠키·`localStorage`) 상관없지만, **잃어버리면 폴링이 404가 되고
사용자는 자리를 잃은 것처럼 보인다.** 그때는 같은 `identifier`로 `enqueue`를 다시 부르면
`already: true`로 원래 자리를 되찾는다 — **그래서 `identifier` 재사용이 중요하다.**
단 그 응답의 `rank`가 `-1`이면 자리를 되찾은 것이 아니라 **이미 입장권이 나간 것**이다
(위 §2의 `rank: -1` 절).

## 4. 브라우저 폴링 — 엔드포인트가 둘이다

### ① 전광판 `/status` — 평상시엔 이것만 부른다

```
GET /api/v1/queues/{queueId}/status        인증 없음 · Rate Limit 없음
```
```json
{ "lastAdmittedSeq": 47,
  "pacing": [[50,2],[1000,5],[5000,10],[10000,15],[null,20]] }
```

**응답이 30만 명 전원에게 동일하다.** 개인화가 없어서 캐시가 가능하고, 그래서 제한도 없다.

#### 🔴 `enqueue`가 **한 번도 없었던 큐**는 `404 Q001`이다

큐를 정상적으로 만들었어도, **첫 `enqueue` 전까지는** 이 엔드포인트가 `404 Q001`
("대기열을 찾을 수 없습니다")을 준다. **없는 `queueId`와 응답이 같아서 구분할 수 없다.**

| 시점 | `/status` |
|---|---|
| 큐 생성 직후 (`enqueue` 0회) | **404 `Q001`** |
| 누가 한 명이라도 선 뒤 | 200 |
| 전원 `admit`돼 줄이 빈 뒤 | 200 (되돌아가지 않는다) |

즉 **오픈 직전에만** 나는데, 하필 그때가 "곧 오픈합니다 / 현재 대기 0명" 페이지를 띄우는 시점이다.
아래 예제들이 `.data`를 바로 펼치므로 **방어하지 않으면 `TypeError`로 죽는다**(실측).

```js
async function getStatus() {
  const res = await fetch(`${P}/api/v1/queues/${queueId}/status`);
  if (res.status === 404) return null;      // 아직 아무도 안 섰다 = 오픈 전. 오류가 아니다
  if (!res.ok) return null;                 // 그 밖의 실패도 다음 주기에 다시 물어본다
  return (await res.json()).data;
}
```

- **내 순위** = `mySeq - watermark` (직접 계산한다. 서버는 rank를 주지 않는다)
- **다음 호출 간격** = `pacing`에서 **내 순위 이하인 첫 구간**의 초 + **지터**

```js
const status = await getStatus();                   // 위 §4① — 오픈 전이면 null이다
if (!status) return setTimeout(tick, 2000);         // 오류가 아니다. 다음 주기에 다시 묻는다

// 🔴 lastAdmittedSeq를 그대로 쓰지 마라 — 단조 clamp가 필요하다
wm = Math.max(wm, status.lastAdmittedSeq);          // wm은 호출 간에 유지한다
const rank = Math.max(0, QUEUE.seq - wm);

const base = status.pacing.find(([max]) => max === null || rank <= max)[1];
const waitMs = (base + Math.random() * Math.max(1, base / 4)) * 1000;
```

> 🔴 **`wm` 단조 clamp를 빼면 순위가 뒤로 갔다 앞으로 갔다 한다.** API 서버가 N대이고
> **세션 어피니티가 없어서**, 방금 받은 `lastAdmittedSeq`가 직전 값보다 **작을 수 있다**.
> 그대로 쓰면 사용자 화면에서 순위가 역행한다.

> 🪤 **지터를 빼지 마라.** 30만 명이 같은 표를 보고 있어서, 지터가 없으면 전원이 같은 초에 몰린다.
>
>
> 규약은 **비대칭(하한 위로만)** 으로 확정됐다 — 위 예시가 그것이다. 대칭(±20%)이면 실효 간격이
> 등급 하한 아래로 내려가 계약 ③의 한도에 더 빨리 닿는다. 서버가 간격을 계산하지 않으므로
> **서버는 이 값을 강제할 수 없다.** 직접 짜는 대신 아래 SDK를 쓰면 이미 지켜져 있다.

### ② 개인 폴링 `/tokens/{tokenId}` — **차례가 가까울 때만**

```
GET /api/v1/queues/{queueId}/tokens/{tokenId}?seq={mySeq}     인증 없음
```
```json
{ "ready": true, "admitToken": "at_xxx" }     // ready=false면 admitToken은 null
```

`rank <= 0`이 되면(= 내 차례가 됐을 수 있으면) 이쪽을 부른다. **평상시에 이걸 부르면 안 된다** —
아래 계약 ③의 한도에 그대로 걸린다.

> **폴링이 곧 생존 신호다.** 이 호출이 대기자의 `last-active`를 갱신한다.
> `?ka=` 파라미터는 **무시된다**(하위호환으로 남아 있을 뿐).
>
> 🔑 **위 두 문장은 모순이 아니다.** 회수 기준이 폴링 여부에 따라 갈리기 때문이다 —
> `last-active`는 **개인 폴링이 만든다**(`enqueue`는 심지 않는다).
>
> | 상태 | 회수 기준 |
> |---|---|
> | 개인 폴링을 **한 번도 안 함** (= 평상시 `/status`만) | `last-active`가 없어 이탈 판정 대상이 **아니다**. `waitingTtl`(기본 **7200초**)이 유일한 회수 경로 |
> | 개인 폴링을 **시작한 뒤 중단** | 그때부터 `inactiveTtl`(기본 **300초**) 대상. 창을 넘기면 회수 |
>
> 즉 자제해도 300초에 잘리지 않는다. **차례가 온 뒤에 부르기 시작했다면 그때부터는 계속 불러라** —
> 폴링을 시작해 놓고 멈추는 것이 이탈 신호다.

## 5. Admit — 받을 수 있는 만큼만 당겨 간다 (Tenant 서버)

```bash
curl -X POST https://<platform>/api/v1/queues/{queueId}/admit \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"count": 50, "requestId": "adm-2026-08-25T10:00:00Z-01"}'
```

```json
{ "isSuccess": true,
  "data": { "admitted": [
    { "tokenId":"tk_...", "identifier":"0192f3c1-...", "seq":1042, "admitToken":"at_..." } ] } }
```

- `count` **최대 300**. 초과하면 400이다
  > 🔴 **300은 "안전한 값"이 아니라 "허용 상한"이다.** 안전값은 당신의 처리 속도가 정한다:
  >
  > ```
  > count ≤ μ × 60초 × 안전계수      (μ = 당신이 초당 앉히는 사람 수)
  > ```
  >
  > 받은 N장을 한 명씩 앉히면 **꼬리는 `N/μ`초 뒤에 앉는다.** `admitToken` TTL은 60초이고
  > **발급 순간부터** 흐르므로, 그 값이 60을 넘는 만큼은 앉기 전에 만료된다.
  >
  > | 당신의 μ | 안전한 count | 300을 쓰면 |
  > |---|---|---|
  > | 3명/초 | **186** | 꼬리가 100초 → 약 40%가 만료 |
  > | 5명/초 | 300 | 꼬리 60초 — 경계다 |
  > | 9명/초 | 564(상한 300) | 안전 |
  >
  > 실측(2026-09-23): μ=2~4명/초인데 `count=300`으로 부르자 발급의 **29%**가 TTL을 넘겨
  > verify·complete가 **404**를 받았다. Platform은 이걸 막아주지 않는다 — **당신이 요청한
  > 수만큼 발급한다.** μ를 모르면 작게 시작해서 올려라(올리는 건 안전하다).
  >
  > 🪤 워커를 여러 개로 나눠 병렬로 앉히면 μ가 그만큼 커진다 — μ는 **팀 전체의 초당 처리량**이다.
- `requestId`는 **멱등 키**다. 같은 값으로 재시도하면 **같은 목록**이 돌아온다.
  네트워크 타임아웃 때 그냥 같은 `requestId`로 다시 불러라 — 중복 입장이 생기지 않는다
- **Platform은 admit을 먼저 걸지 않는다.** 빈 좌석이 생겼을 때 **Tenant가 부르는 것**이다
  (Backpressure Pull). 안 부르면 줄은 그대로 서 있는다

`admitToken`은 이 응답에서 발급되고 **그 순간부터 TTL이 흐른다**. 브라우저 폴링은 이미 발급된
값을 **전달만** 한다 — 폴링이 늦었다고 시계가 늦게 가지 않는다.

## 6. Verify / Complete — 둘 중 **하나만** 부른다

```bash
# verify — admitToken이 유효한지 확인하고 identifier를 받는다
curl -X POST .../api/v1/queues/{queueId}/admit-tokens/{admitToken}/verify -H "X-API-Key: $API_KEY"
# → { "data": { "identifier": "0192f3c1-..." } }

# complete — 입장 완료를 통보한다
curl -X POST .../api/v1/queues/{queueId}/tokens/{tokenId}/complete \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"admitToken": "at_..."}'
# → { "data": { "status": "COMPLETED", "completedAt": "2026-08-25T10:00:03.412Z" } }
```

### 🔑 **하나만 골라라 — 둘 다 부르지 마라**

둘 다 불러도 답은 맞다(두 번째 호출은 처음 완료 시각을 돌려준다). 그런데 **두 번째 호출은 일을
두 배로 만든다**: `verify`가 이미 완료를 확정했으므로 뒤따르는 `complete`의 `UPDATE`는 **0행**이고,
그 0행을 확인하려고 `SELECT`가 한 번 더 나간다.

실측 근거(AWS 8차, 500만 명):

```
complete UPDATE  454만 회 / MySQL CPU 5,662초   ← 그중 97.3% 가 0행이었다
complete SELECT  442만 회 / MySQL CPU 4,196초   ← 그 0행을 확인하는 조회
                          합계 9,858초 = 쿼리 예산의 35.9%
```

DB 노드 CPU 가 판 내내 85~95% 였고, **그 3분의 1이 "이미 끝난 일을 다시 확인하는" 비용**이었다.
서버는 거절하지 않는다 — 거절할 근거가 없다. 그래서 **계약으로 요청한다.**

| 당신의 상황 | 부를 것 |
|---|---|
| `identifier`(누구인지)가 필요하다 | **`verify` 하나만** |
| `identifier`가 필요 없다 / 이미 알고 있다 | **`complete` 하나만** |
| 내부 좌석 배정이 **60초를 넘길 수 있다** | **`complete` 하나만** (계약 ⑤) |

### ⚠️ 예외 하나 — `verify`가 `TK002`로 404면 **그때는 `complete`를 불러라**

`verify`의 창은 60초고 `complete`의 창은 300초다(계약 ⑤). 그래서 **내부 처리가 60초를 넘겨
`verify`가 `TK002` 404를 주는 경우**가 있는데, 그건 "자격이 없다"가 아니라 **"`verify`의 창만
지났다"**는 뜻이다. 아직 완료를 확정할 수 있다.

```
admit → [내부 좌석 배정 90초] → verify → 404 TK002
                                      └→ complete → 200  ✅ 여기서 확정된다
```

🔑 **`verify`가 404였으면 완료가 확정되지 않았다.** 그냥 두면 원장에 `ADMIT_ISSUED`로 남고
대사 배치가 만료로 정리한다 — 당신의 완료율 지표가 틀어진다. **404를 받으면 반드시 `complete`를
이어 불러라.**

⚠️ 단 `complete`도 300초를 넘기면 `TK002` 404다. 그 뒤로는 되살릴 방법이 없다.

🔴 **300초 안에 받은 `complete`의 `TK002`는 일시적일 수 있다 — 입장 후 300초까지는 재시도하라.**
Platform 내부 적재(Kafka → DB)가 밀린 동안에는 **입장 60초 뒤 ~ 적재 완료 전** 구간의 `complete`가
404를 준다. 적재가 끝나면 **같은 요청이 200이 된다**. 당신 쪽에서는 이 404와 진짜 무효를 구분할 수
없으므로, 입장(admit 응답) 후 300초가 지나기 전까지는 몇 초 간격으로 다시 불러라.

```
실측(2026-09-25 로컬, 적재 정지로 재현):  입장 82초 complete → 404 TK002
                                          적재 재개 · 입장 101초 같은 요청 → 200 (원장 status=2)
AWS 500만 판: 적재 지연 구간에서 이 404가 30.8만 건 났다 — 재시도했다면 살았을 입장자다
```
🪤 재시도는 **404에만** 한다. 200을 받았으면 끝이다(바로 아래).

🪤 **적재 지연 구간에서 받은 200은 재시도하면 안 된다.** `complete`는 DB를 먼저 보고, 컨슈머가
아직 `ADMITTED`를 적재하지 않아 0행이면 **Redis로 폴백**해 200을 준다. 그때는 Redis 키가
소비되므로 **같은 요청을 재시도하면 404**가 날 수 있다. **200을 받았으면 완료된 것이다.**
(자세한 판정 순서는 [`API.md`](API.md) §4 complete)

## 🔴 계약 8건 — 어기면 어떻게 되는지까지

### ① `verify`와 `complete` 중 **정확히 하나**를 부른다

`verify`는 **응답을 주는 시점에 완료를 확정한다**. Platform의 책임은 답을 돌려주는 데까지이고,
그 뒤 Tenant 안에서 좌석 배정이 어떻게 되는지는 관측할 수도 책임질 수도 없기 때문이다.
그래서 `complete`를 덧붙일 이유가 없다 — **이미 끝난 일을 다시 확인하는 DB 왕복 두 번**이다.

| 부른 것 | 결과 |
|---|---|
| `verify`만 | ✅ **권장.** 완료 확정 + 자리 반납 — 그 뒤 같은 `identifier`의 `enqueue`는 **신규·맨 뒤**다(`complete`만과 같다, §92) |
| `complete`만 | ✅ **권장.** 완료 확정. **`verify`를 건너뛴 호출을 서버가 거절하지 않는다** — `complete` 자체가 `admitToken`을 검증하므로 거절할 근거가 없다 |
| 둘 다 | 🟠 **틀리지는 않지만 하지 마라.** 답은 맞다(두 번째는 처음 완료 시각). 대가는 `UPDATE` 0행 + 확인 `SELECT`이고, AWS 8차에서 그게 **DB 쿼리 예산의 35.9%** 였다 (§6) |
| `verify` → **404 `TK002`** → `complete` | ✅ **이것은 예외다 — 이어 불러야 한다.** `verify`의 창(60초)만 지난 것이고 `complete`의 창(300초)은 살아 있다 (§6 · 계약 ⑤) |
| **아무것도 안 부름** | 🔴 원장에 `ADMIT_ISSUED`로 남고, **대사 배치가 300초 뒤 만료로 정리**한다 |

> 마지막 줄이 요금을 바꾸지는 않는다(과금은 상태를 보지 않는다). 다만 **Tenant의 완료율 지표가
> 통째로 틀어진다.**
>
> 🔑 **"하나만"이 안전한 이유**: 예전에는 `verify`만 부르면 자리 반납 시점이 `complete`와 달라
> 과금이 경로에 따라 1 vs 2로 갈렸다. §92에서 `verify`도 Redis를 정리하게 바뀌어 **두 경로가
> 같아졌다.** 그래서 지금은 어느 쪽 하나를 골라도 결과가 같다.

### ② `429`는 **두 가지**다 — `errorCode`를 보고 갈라라

🔴 **HTTP 상태만 보고 재시도하면 안 된다.** `enqueue`의 429는 뜻이 둘이고, 대응이 반대다.

| `errorCode` | 뜻 | `Retry-After` | 대응 |
|---|---|---|---|
| `RL001` | 요청 한도 초과 (Token Bucket) | ✅ **붙는다** | 그 초만큼 기다렸다 재시도 |
| `Q005` | **대기열 정원이 찼다** (`maxCapacity` 도달) | ❌ **안 붙는다** | **재시도하지 마라.** 계약 ⑦ |

`Retry-After`를 붙이는 것은 Rate Limit 필터뿐이다. `Q005`는 그 필터를 지나온 **정상 처리 결과**라
헤더가 없다 — **헤더가 없으면 `Q005`다.** 정원이 언제 빌지는 서버도 모르므로 정직한 숫자를
낼 수 없어서 안 붙인다.

🪤 **두 429는 본문 모양도 다르다**(실측). `RL001`은 Rate Limit 필터가 `ApiResponse` 봉투 없이
직접 쓰고, `Q005`는 애플리케이션 응답이라 봉투를 탄다. 봉투만 보면 `RL001`을 놓친다.

```
RL001 : {"error":"RL001","message":"요청 한도를 초과했습니다.","retryAfter":2}
Q005  : {"data":null, ..., "errorResponse":{"code":"Q005","message":"..."}}
```

```js
if (res.status === 429) {
  const code = body.errorResponse?.code ?? body.error;   // 두 모양을 다 읽는다
  if (code === "Q005") return showFullPage();            // 재시도 금지
  await sleep(res.headers.get("Retry-After") * 1000);    // RL001
  return retry();                                        // identifier가 같으면 중복 안 생긴다
}
```

🪤 **`RL001` 429를 오류 화면으로 띄우지 마라.** 사용자는 자리를 잃지 않았고, 잠깐 너무 자주
물어본 것뿐이다. 같은 `identifier`로 재시도하면 중복이 생기지 않는다.

| 어디 | 한도 | `Retry-After` |
|---|---|---|
| Tenant API (`enqueue`/`admit`/…) | Token Bucket (`RL001`). **모든 테넌트 동일** | refill 기준 값 |
| 브라우저 폴링 | 아래 ③ | **2초** |

### ③ **한 `tokenId`의 폴링 한도는 탭·기기를 통틀어 하나다**

버킷 키가 `tokenId` 하나다. **용량 5, 초당 1개 충전.**

```
탭 1개  → 여유 4
탭 2개  → 여유 0        ← 이미 아슬아슬하다
탭 3개  → 10초 안에 429
```

같은 사용자가 **탭을 두 개 열면 그 둘이 한 버킷을 나눠 쓴다.** 기기가 달라도 마찬가지다 —
IP가 아니라 `tokenId`가 키이기 때문이다.

**대응**: 탭 하나만 폴링하게 만들어라. 서버 변경 없이 클라이언트만으로 된다.
**`sdk/js/`가 이것 하나 때문에 존재한다** — 직접 짜는 대신 그걸 쓰면 된다(아래 §7).

SDK는 리더 선출에 **Web Locks(`navigator.locks`)** 를 쓴다. 탭이 닫히면 브라우저가 락을 자동으로
놓아 다음 탭이 이어받으므로, 하트비트도 타임아웃도 필요 없다. 나머지 탭의 화면 갱신에만
`BroadcastChannel`을 쓴다. 실측: 탭 3개 30초 동안 API 요청이 `3 / 0 / 0`이고, 리더 탭을 닫으면
두 번째 탭이 이어받는다.

> 이것이 **평상시 폴링을 `/status`로 보내야 하는 이유**다. `/status`는 제한이 없다.

### ④ **입장권 1장 ≠ 세션 1개**

`admitToken`은 **"줄을 통과했다"는 증명**이지 로그인 세션이 아니다. Platform은 세션을 만들지 않고,
동시 접속 수도 세지 않는다.

- `verify`가 돌려준 `identifier`로 **Tenant가 자기 세션을 만든다**. 그때부터는 Tenant 소관이다
- 한 사용자가 통과한 뒤 **탭을 여러 개 여는 것을 Platform은 막지 않는다.**
  그걸 막아야 하면 Tenant의 세션 계층에서 해라
- 반대로 **Tenant 세션이 끊겨도 Platform은 모른다.** 다시 줄을 세우려면 `enqueue`를 다시 불러야 하고,
  그건 **맨 뒤**다

### ⑤ **`verify`는 60초, `complete`는 300초** — 창이 다르다

| 호출 | 유효 창 | 기준 시각 |
|---|---|---|
| `verify` | **60초** | `admit` 응답 시점 |
| `complete` | **300초** | `admit` 응답 시점 |

`verify`는 `admitToken`의 Redis 키(PX 60초)에 기대고, `complete`는 DB의 `admitted_at`을 300초까지
소급해 받아 준다. **비대칭은 의도한 것이다** — 좌석 배정이 오래 걸린 Tenant의 **늦은 완료 통보**를
받아 주기 위해서다(실측: admit 후 **98초**에 온 `complete`가 정상 200이었다).

**그래서 어느 쪽 하나를 부를지가 "언제 부를 수 있는가"로 결정된다.** 계약 ①이 "하나만"인데,
그 하나를 고르는 기준이 이 창이다.

```
❌  admit → [내부 좌석 배정 90초] → verify              → TK002 404 (창 60초를 넘겼다)
                                        └→ complete    → 200  (예외 경로로 살린다, §6)

✅  admit → verify → [내부 좌석 배정 90초]              → 끝. complete 부르지 않는다
    (identifier 가 필요할 때. verify 응답 시점에 이미 완료다)

✅  admit → [내부 좌석 배정 90초] → complete             → 200
    (identifier 가 필요 없을 때. 창이 300초라 여유가 다섯 배다)
```

🔑 **`identifier`가 필요하면 `verify`를 내부 처리 *전에*** 불러라 — 뒤로 미루면 60초 창을 넘긴다.
그리고 그 `verify`가 곧 완료이므로 **뒤에 `complete`를 붙이지 마라**(계약 ①).

🔑 **`identifier`가 필요 없으면 `complete` 하나만** 불러라. 창이 300초라 늦은 통보에 강하다.

⚠️ 실수로 `verify`를 늦게 불러 `TK002` 404를 받았다면 **거기서 멈추지 말고 `complete`를 이어
불러라** — 그것이 §6의 예외다. 안 부르면 그 입장자는 완료로 기록되지 않는다.

### ⑥ **`enqueue` 직후에 폴링하지 마라 — 첫 호출은 `setTimeout`으로 예약한다**

`enqueue` 응답이 이미 `tokenId`·`seq`·`rank`·`total`을 준다. 그래서 직후 폴링은
**새 정보를 하나도 주지 않으면서 한도만 태운다.**

```js
// ❌ 하지 마라 — rank는 이미 손에 있다
const { tokenId, seq, rank } = enq.data;
poll(tokenId, seq);                       // 버킷 5칸 중 1칸 소모, 얻는 것 없음

// ✅ 첫 호출부터 pacing 간격으로 예약한다
const { tokenId, seq, rank } = enq.data;
const s = await getStatus();                              // /status는 한도가 없다
// 🔴 오픈 전이면 null이다(§4①의 404 Q001). 그때는 기본 간격으로 예약하고 다음 주기에 다시 묻는다
const base = s ? s.pacing.find(([max]) => max === null || rank <= max)[1] : 2;
setTimeout(tick, (base + Math.random() * Math.max(1, base / 4)) * 1000);   // 지터 필수
```

**깨지지는 않는다 — 낭비가 문제다.** 실측(2026-08-28):

| 잰 것 | 결과 |
|---|---|
| `enqueue` → **0ms** 개인 폴링 ×20 (매번 새 토큰) | **20/20 200.** `404` 경합 없음 |
| 같은 `tokenId`로 연속 폴링 ×8 | `200 ×5` → **`429 ×3`** (계약 ③의 cap 5 / refill 1.0/s) |
| `/status` 연속 20회 | **20/20 200.** 한도 없음 |

즉시 폴링이 안전한 이유는 `enqueue`가 **순번을 확정한 뒤에** 응답하기 때문이다 — 응답에 `seq`가
들어 있다는 것 자체가 Redis에 이미 들어갔다는 뜻이라, 폴링이 못 찾을 창이 없다.
(DB 적재는 뒤에서 비동기로 돌지만 폴링은 그것을 보지 않는다.)

> 🔴 **낭비가 왜 치명적인가.** 버킷은 cap 5 · refill 1.0/s이고 키가 `tokenId` 하나다(계약 ③).
> 진입 순간에 1칸을 태우면 **정작 차례가 왔을 때 여유가 4에서 시작**한다. 탭이 2개면 그 여유를
> 나눠 쓰므로 사실상 0이다. `admitToken`을 받아야 하는 바로 그 순간에 `429`를 맞는다.
>
> 🪤 **개인 폴링을 시작하면 `inactiveTtl`(기본 300초) 대상이 된다**(§4 ②의 표).
> 즉시 폴링은 아직 차례가 한참 남았는데 **이탈 판정 시계를 미리 켜는 것**이기도 하다.

### ⑦ **상한이 둘 있다 — 큐의 정원 30만, 테넌트당 큐 20개**

| 상한 | 값 | 어길 때 | 언제 |
|---|---|---|---|
| `maxCapacity` | **1 ~ 300,000** | `400` (Bean Validation) | 큐 생성 |
| 큐가 정원에 도달 | 위 값 | **`Q005` 429** (`Retry-After` 없음) | `enqueue` |
| 테넌트당 큐 개수 | **20** | **`Q006` 409** | 큐 생성 |

**왜 상한이 있나 — 남의 큐를 지키기 위해서다.** 한 큐의 키는 Redis 마스터 **한 대에** 고정된다
(해시태그, 큐 수명 동안 안 바뀐다). 대기자 1명당 **477 B**(실측)이므로 상한 없는 큐 하나가
그 마스터를 채우면 **같은 마스터에 사는 다른 테넌트의 `enqueue`가 죽는다.** 그때 폴링(읽기)은
살아 있어서, 대기자에게는 "줄은 보이는데 못 들어가는" 상태로 보인다.

**정원이 찼을 때 무엇을 할 것인가** — 재시도는 답이 아니다. 자리는 앞사람이
`complete`하거나 TTL로 빠져야 생기고, 그 시점은 예측할 수 없다.

- ✅ **대기열 마감 페이지를 보여준다.** `Q005`는 "지금 줄에 못 선다"이지 오류가 아니다
- ✅ 정원이 상시 부족하면 **큐를 나눈다**(회차·좌석 등급별). 큐당 30만이 상한이지 총량이 아니다
- ❌ **`maxCapacity`를 30만 위로 올려달라고 요청하지 마라** — 위 이유로 거절된다
- 🪤 **`Q005`를 받고 같은 `identifier`로 재시도해도 자리가 생기지 않는다.** 중복은 안 생기지만
  (`identifier`가 게이트다) 정원 판정은 매번 새로 한다

**큐 개수 20개**는 `DELETED`를 세지 않는다 — 큐를 지우고 **다른 이름으로** 다시 만드는 운용은
막히지 않는다. (같은 이름은 상한과 무관하게 `Q003`으로 막힌다. 큐 이름은 테넌트 안에서 유일하다.)

> |---|---|---|
> | `rl:tenant:{id}` | **enqueue** | 50,000 · 초당 833 |
> | `rl:tenant:{id}:drain` | **admit · verify · complete** | 50,000 · 초당 833 |
> | `rl:tenant:{id}:control` | 큐 생성·수정·삭제·pause·resume·API Key | **60 · 초당 1** |
>
> 🔑 **줄을 세우는 것과 빼는 것이 서로 굶지 않는다.** 예전엔 한 지갑이라, 유입이 한도를 다 쓰면
> `admit` 이 429 가 되어 **줄이 안 빠지고 더 쌓이는 악순환**이 됐다. 제어도 마찬가지여서
> **부하가 몰린 순간에 `pause` 가 안 눌렸다**(실측).
>
> 🪤 **큐를 여러 개 써도 한도는 하나다** — 큐당 한도가 필요하면 **테넌트를 나눠야 한다.**

버킷 키가 `rl:tenant:{테넌트}` 하나다. **`queueId`가 키에 없다.** 큐를 20개 만들어도 한도는
그 20개가 **나눠 쓴다.**

| 테넌트의 큐 수 | 큐당 지속 `enqueue` rps |
|---|---|
| 1개 | 277 |
| 2개 | 138 |
| 5개 | 55 |
| 20개 (계약 ⑦ 상한) | 14 |

🔑 **버킷을 먹는 것은 `enqueue`만이 아니다.** `verify`·`complete`·`admit`도 같은 버킷을 쓴다.
유저 1명이 끝까지 가면 **3.01건**을 소비한다(`enqueue` 1 + `verify` 1 + `complete` 1 +
`admit` 1/20). 위 표는 그걸 반영한 값이다. 중간에 이탈하는 유저는 `enqueue` 1건만 먹으므로,
이탈률이 높으면 실제 수용은 표보다 늘어난다.

**브라우저 폴링은 여기 안 들어간다** — 계약 ③의 별도 버킷(`tokenId` 단위)을 쓴다. 큐에 30만 명이
서 있어도 이 한도와 무관하다. 제한되는 것은 **문을 새로 통과하는 속도**뿐이다.

🪤 **오픈 순간은 다르다.** 몰리는 그 순간에 소비되는 것은 `enqueue` 1건뿐이고(`verify`·`complete`는
몇 분 뒤에 온다), 버킷에 **1분치가 미리 차 있다.** 그래서 **동시 5만 명까지는 0초에 통과한다.**
위 표의 숫자는 그 1분치를 다 쓴 뒤의 지속 속도다.

> 큐를 더 만들어서 한도를 늘릴 수는 없다. 그게 이 한도의 목적이다 — 한 테넌트가 플랫폼을
> 독식하지 못하게 하는 것. 한도가 모자라면 큐를 쪼개지 말고 문의하라.


## 🔴 큐를 멈추거나 지울 때 (2026-09-16)

`pause`는 **입구만 잠근다.** `delete`는 **되돌릴 수 없다.**

| | 신규 유저 | **이미 줄 선 유저** | `admit` | `verify`·`complete` |
|---|---|---|---|---|
| `pause` | ❌ `503 Q004` | ✅ 그대로 유지 · 새로고침해도 **자리 보존** | ✅ | ✅ |
| `delete` | ❌ | ❌ **줄이 사라진다** | ❌ `404 Q001` | ✅ **300초간 허용** |

### 🪤 멈춰도 시간은 흐른다

`pause`는 **대기자를 보존하는 기능이 아니다.** 멈춰둔 동안에도 회수 배치는 계속 돌고,
대기자는 `inactiveTtl`(폴링이 끊긴 뒤)·`waitingTtl`(줄 선 지 오래된 뒤)로 정리된다.

- **30분 멈췄다가 재개하면 줄이 비어 있을 수 있다.** 그게 정상이다
- 그렇게 사라진 토큰도 **청구 대상이다**(과금은 발급 기준이고 상태와 무관하다)
- 짧은 점검이면 상관없지만, **"이벤트를 내일로 미룬다"면 멈추지 말고 안내하라**

> 이렇게 하지 않으면 멈춰둔 큐가 Redis를 무기한 점유하고, 같은 서버를 쓰는 **다른 테넌트의
> enqueue가 죽는다.** 그래서 멈춰도 시간은 흐르게 두었다.

### 🪤 지우면 줄도 사라지고, 되살릴 수 없다

- `delete`는 **`pause` 상태에서만** 된다(`ACTIVE`에서 바로 부르면 `409 QE006`)
- 지우는 순간 **대기 줄이 즉시 삭제**된다. 대기자에게는 사전 통지가 없다
- `DELETED`에서 나가는 전이는 **없다.** 같은 큐를 되살릴 수 없고, 새로 만들어야 한다
  (🪤 **같은 이름은 못 쓴다** — 이름 중복 검사는 삭제된 큐도 본다)
- **이미 나간 입장권은 살려준다** — 삭제 시점에 좌석으로 가던 사용자의 `verify`·`complete`는
  300초 동안 그대로 성공한다. 그 사용자에게서 돈을 받았으니 입장은 시켜주는 것이 맞다

## 7. 폴링은 SDK를 써도 된다 (`sdk/js/`)

§4의 폴링 로직을 직접 짜지 않아도 된다. 빌드도 의존성도 없는 ESM 한 파일이다.

```html
<script type="module">
import { createQueueClient } from '/sdk/js/queue-sdk.js';

createQueueClient({
  baseUrl: 'https://queue.example.com',
  queueId: QUEUE.queueId, tokenId: QUEUE.tokenId, seq: QUEUE.seq,   // §3에서 내려보낸 값
  onUpdate: ({ rank }) => render(rank),
  onReady:  ({ admitToken }) => goToService(admitToken),
}).start();
</script>
```

**범위는 폴링 GET 둘뿐이다.** `enqueue`·`admit`·`verify`·`complete`는 들어 있지 않다 —
전부 `X-API-Key`가 필요하고, 그 키는 §1에 따라 Tenant 서버에만 둔다.

SDK가 대신 지켜 주는 것은 **직접 짜면 틀리기 쉬운 넷**이다: 워터마크 단조 clamp(§4),
비대칭 지터(§4), 리더 탭(계약 ③), 개인 폴링을 시작했으면 멈추지 않기(계약 ⑥).
두 429의 다른 본문 모양(계약 ②)도 SDK가 흡수한다.

> 대기 페이지가 Platform과 **다른 오리진**이어도 된다. 공개 폴링 GET 둘에만 CORS가 열려 있고,
> 429의 `Retry-After`도 노출된다. 그 밖의 경로는 닫혀 있다 — 브라우저에서 `enqueue`를 시도할
> 수 없다는 뜻이기도 하다.

## 에러 코드

| 코드 | HTTP | 뜻 | 대응 |
|---|---|---|---|
| `RL001` | 429 | 요청 한도 초과 | `Retry-After`만큼 대기 후 재시도 |
| `Q001` | 404 | 대기열 없음 — **또는 아직 아무도 안 선 큐**(§4①) | `/status`면 오류가 아니다(오픈 전). 그 밖이면 `queueId`를 확인하라 |
| `Q005` | 429 | **대기열 정원이 참** (`maxCapacity` 도달) | 🔴 **재시도 금지.** 마감 페이지. `Retry-After` 없음 — 계약 ②·⑦ |
| `Q006` | 409 | 테넌트당 큐 개수 상한(20) 초과 | 안 쓰는 큐를 지우고 다시 만들어라. 계약 ⑦ |
| `QE001` | 503 | 대기열 처리 일시 오류 | 재시도. `enqueue`면 같은 `identifier`로 안전하다 |
| `TK001` | 404 | 대기 토큰 없음 | 폴링 중이면 자리를 잃은 것. 같은 `identifier`로 `enqueue` 재시도 |
| `TK002` | 404 | 입장 토큰 무효 | 창(60초)을 넘겼거나 잘못된 값. 🔴 **`complete`에서 입장 후 300초 안이면 일시적일 수 있다 — 재시도.** 계약 ⑤ 참조 |

## 흔한 실수 8가지

1. 🔴 **대기 페이지에 `seq`를 안 내려보낸다** → 폴링이 아예 안 된다 (§3)
2. 🔴 **사용자마다 매번 새 `identifier`를 만든다** → 새로고침할 때마다 맨 뒤로 간다 (§2)
3. 🔴 **평상시에도 개인 폴링을 부른다** → 계약 ③에 걸려 429. 평상시는 `/status`다
4. 🔴 **`verify`를 내부 처리 뒤에 부른다** → 60초 창을 넘겨 `TK002` (계약 ⑤).
   그 404에서 멈추지 말고 **`complete`를 이어 불러라** — 300초 창이 살아 있다 (§6)
4-1. 🟠 **`verify`와 `complete`를 둘 다 부른다** → 답은 맞지만 **DB 왕복 두 번이 헛일**이다.
   AWS 8차에서 그 헛일이 DB 쿼리 예산의 **35.9%** 였다. 하나만 골라라 (계약 ①)
5. 🟠 **폴링 간격에 지터를 안 넣는다** → 30만 명이 같은 초에 몰린다 (§4)
6. 🟠 **429를 오류 화면으로 띄운다** → `RL001`이면 사용자는 자리를 잃지 않았다 (계약 ②)
6-1. 🔴 **429를 `errorCode` 없이 뭉뚱그려 재시도한다** → `Q005`(정원 참)에 무한 재시도가 된다.
   `Retry-After`도 없어서 백오프 근거조차 없다 (계약 ②·⑦)
7. 🟠 **`enqueue` 직후 곧바로 폴링한다** → 깨지진 않지만 버킷 1칸을 헛되이 태우고
   이탈 판정 시계를 미리 켠다. 첫 호출부터 `setTimeout` (계약 ⑥)
