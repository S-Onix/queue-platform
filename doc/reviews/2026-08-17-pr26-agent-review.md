## 2. 종료 기준 — 왜 필요했나

2차 판정에서 `lead`가 진단했다:

> 라운드가 늘어나는 이유는 검토가 부실해서가 아니다. **§78·§79가 미구현 기능**(admit, `/status`,
> watermark — 전부 코드 0줄)**의 계약을 문서로 확정하려 하기 때문**이다. 미구현 영역은 지적을
> 무한히 생산할 수 있다. "문서가 완전해지면 끝"은 종료 조건이 아니다.

그래서 종료 조건을 이렇게 못 박았다:

> **"이 PR이 스스로 한 주장 중 거짓이 0"**. 문서의 완전성이 아니다.
> 3라운드의 새 지적은 예외 없이 후속 목록행이고 커밋을 막지 않는다.
> **단 하나의 예외: "이 PR의 문장이 거짓임을 보이는 지적."**

이 기준이 없었으면 끝나지 않았다. 실제로 3라운드에서 architect가 찾은 2건이 정확히 그 예외에
해당해 반영됐고, security가 찾은 1건(admit 처리 흐름의 소유권 검증 부재)은 "PR이 그렇게 단언한
적이 없다"는 이유로 후속행이 됐다.

## 3. `/status` 오리진 부하 — 근거가 네 번 뒤집혔다

이 프로젝트에서 한 항목의 근거가 이만큼 연속으로 깨진 적이 없다. 매번 **다른 주체**가 잡았다.

| # | 안 | 왜 깨졌나 | 뒤집은 곳 |
|---|---|---|---|
| ① | **IP 기반 Rate Limit** | 증폭 경로를 막으면 RL이 방어할 잔여가 없다. 1요청 = 값싼 404 하나면 `/status` 고유 문제가 아니라 모든 공개 엔드포인트에 공통인 L7 flood이고 CDN·WAF 소관이다 | **`lead`가 자기 원안을 스스로 기각** |
| ② | **캐시 키에서 쿼리스트링 제외 → "요청 수와 무관하게 `1÷TTL` 상수"** | cache-buster는 쿼리스트링에만 있지 않다. **경로 자체**(`/queues/{임의}/status`)가 매번 새 캐시 키다. 유효 큐에 대해서만 참 | `architect` |
| ③ | **미지 queueId를 CDN negative cache** | negative cache는 *같은* 키를 반복 요청할 때만 듣는다. 미지 ID는 매번 새 키라 **엔트리 재사용이 0**이고 메모리만 는다 | `lead` |
| ④ | **맵 선적재 후 "맵에 없으면 404"** | 큐는 런타임 생성(`POST /queues`)이라 **부팅 시 선적재한 맵에 그 이후 만든 큐가 없다.** §75 D27-2의 "매핑 불변"은 **기존 항목**에 대한 말이다 → 새 큐의 `/status`가 WAS 재기동 전까지 404 | `architect` |

**확정안**: 맵 선적재 + **주기적 통째 리로드**(매핑이 불변이라 값 충돌이 없어 통째 교체가 안전).
**미스는 DB로 내려보내지 않는다** — 인증 없는 요청이 MySQL을 때리는 증폭 경로 차단이 이 항목의 목적이다.
**리로드 주기는 미정**이며, 그 값이 곧 "큐 생성 후 `/status`가 열리기까지의 지연"이다.

> 네 번 모두 **"안 깨지는 줄 알았던 전제"가 깨진 것**이다. 한 사람이 계속 봤으면 넷 다 못 잡았다.

## 4. 걷어낸 거짓 문장

| 문장 | 실제 | 잡은 곳 |
|---|---|---|
| "pop + admitToken SET + watermark를 **전부 한 Lua**로 처리" | **Lua는 MySQL을 못 만진다.** 중간에 DB WAITING 확인이 낀다. 게다가 `verified-token:{tokenId}`는 태그가 없어 클러스터 소속이 미정 | `architect` |
| 같은 단정이 **§75 D26·FRS §4.1에도** | 두 문서는 **Sprint 7 구현자가 §79보다 먼저 읽는다**(키 배치 규범 / API 명세). §79의 경고가 무력화된다 | `architect` (3라운드) |
| "WAITING 복귀는 `ZADD {seq} {tokenId}`" | 실제 멤버는 `identifier`(`enqueue_bulk.lua:65`). `poll_verify.lua`가 `ZRANGEBYSCORE` → member → `HGET tokens[member]`로 대조하므로 **멤버가 tokenId면 항상 404** — 이번에 새로 정한 404 재시도 계약이 걸려야 할 상태 B가 도달 불가가 된다 | `architect` |
| "`cap 3`" (문서가 정본, 코드는 후속) | 산술이 결론을 지지하지 않는다(`1.0/s × 2초 = 2`, 그 2배는 **4**). 코드는 `POLL_CAPACITY=5`. **문서-코드 괴리를 갚으러 온 PR이 같은 자리에서 괴리를 다시 만들고 있었다** | `architect` + `security` 독립 발견 |
| "1.5만~6만 rps" | pacing 표 가중 = **15,448 rps**. 6만은 전원이 5초 구간일 때만 나오는데 사다리 구조상 도달 불가 | `architect` |
| "매 폴링이 `ZRANGE`+`ZCARD`+`ZCOUNT`" | `ZCOUNT`는 §74에서 소멸(전 소스 0건). 나머지는 `QueueSnapshotCache` 2초 캐시 뒤. **실제는 `poll_verify.lua` EVAL 1회** | `planner` |
| "개인화 비율 1/15~1/30" | 대다수가 20초 구간이라 실제 **1/2~1/3**. 개인화 트래픽은 500 rps가 아니라 **5,000~7,700 rps** | `architect` |
| 커밋 메시지의 "잔여 서술 **2건** 정리" | `FRS §12`의 `### Java SDK (Tenant 서버용)` **58줄 절 전체**가 살아 있었다 | `planner` |

## 5. 닫은 크로스 테넌트 구멍

- **`admit-idem:{requestId}` → `queue:{queueId}:admit-idem:{requestId}`** (9곳).
  `requestId`는 **Tenant가 정하는 값**인데 키가 전역이었다. Tenant A가 `"req_abc"`를 선점하면
  Tenant B의 admit이 `NX`로 조용히 삼켜지고, 저장된 `{result}`에 admitToken 목록이 들어가면
  그대로 유출된다. **접두어 하나로 스코프와 해시태그가 동시 해결**된다. — `security`
- **verify·complete에 0단계 신설** — API Key tenant의 `queueId` 소유 검증(`QUEUE_NOT_OWNED`).
  enqueue는 `QueueEngineService`가 이미 하고 있었다. complete는 **쓰기**다.
  U5(URL에 `queueId` 추가) 이전에는 검증이 **불가능**했고, U5가 가능하게 만들면서 동시에 필요해졌다.
- **verify DB Fallback에 `queue_id`/`tenant_id` 술어 추가.**
- **admitToken 생성 규정 신설** — `tokenId`와 동일하게 UUIDv7(랜덤 74비트). 짧은 랜덤 금지.
  기존에는 예시가 `at_abc123`(6자)뿐이고 생성 규정이 전 문서 0건인데 **verify는 이 값 하나로 통과**한다.

> 마지막 둘은 따로 보면 각각 🟡인데 **겹치면 색이 바뀐다** — 약한 admitToken + 술어 없는 DB Fallback이면
> 테넌트 무관 무차별 대입으로 남의 큐 입장이 성립한다. **두 지적을 낸 건 `security` 하나지만
> 결합 위험은 아무도 안 적었고, `lead`가 판정 단계에서 결합해 발견했다.**

## 6. 에이전트가 서로를 정정한 것

- `architect`가 **자기 1차 진단을 철회**했다 — "`{queueId}` 태그를 못 붙인다(verify가 admitToken만
  갖고 있으니까)"는 **우리가 쓴 URL 명세를 제약으로 착각한 것**이었다. verify를 부르는 건 Tenant이고
  Tenant는 자기 큐를 안다 → URL에 `queueId`를 넣으면 CROSSSLOT이 소멸한다(U5).
- `architect`가 **`planner`에게 진 것 2건**: "A(admit됨) 판정이 곧 404가 된다" / "EVAL은 write로
  분류돼 전부 master행". 둘 다 planner가 더 깊게 팠다.
- `lead`가 **`security`의 진단을 정정**했다 — "판정 키는 반드시 tokenId 기반이라는 한 줄이 필요"는
  이미 있었고, 진짜 결함은 **§79 내부 모순**이었다. **요구(결론)는 맞고 이유가 틀렸다.**
- `lead`가 **코디네이터의 추천 근거를 두 번 반려**했다 — negative cache(무효) / `cap 3`(산술 오류).

## 7. 남은 후속 (15건) — 조용히 사라지지 않게 여기 못 박는다

**A. 이번 라운드에서 새로 생긴 것**
1. 맵 리로드가 **WAS별 독립**이라 N대 사이 맵이 일시적으로 갈린다 — 같은 새 큐가 WAS A는 200, WAS B는 404.
   U7의 "404는 즉시 종료 아님" 계약이 우연히 덮지만 문서 미기재
2. **enqueue·admit 경로도 같은 맵을 쓰는지 미기재.** 다르면 새 큐 창에서 enqueue만 되고 `/status`만 404
3. `DECISIONS` §79 `미검증` 목록에 **맵 선적재·리로드가 누락** — 이번에 넣은 유일한 새 메커니즘인데 빠졌다

**B. 값이 미정 — 셋이 서로를 정하므로 한 번에 정해야 한다**
4. `/status` **캐시 TTL** — 오리진 부하 ↔ pacing 레버 반영 지연 ↔ 입장 지연을 한 값이 정한다
5. **맵 리로드 주기** — 큐 생성 후 `/status`가 열리기까지의 지연
6. `queue:{queueId}:pacing`의 **"즉시 변경" ↔ "캐시 미스 때만" 모순** — 가장 급할 때 가장 늦게 듣는다

**C. Sprint 7 admit 착수의 입력값**
7. **"pop 성공 + 토큰 SET 실패" 창** — 이 PR은 "미해결"이라 적기만 했다. 해결안 선택이 Sprint 7의 첫 일

## 8. 이 검토가 규칙에 남긴 것

작업 중 사용자가 **협업 규칙 §4(과설계 금지)**를 신설했다. 계기는 `lead`가 1차에 "확정"한
`/status` IP Rate Limit이었다 — 위 §3에서 보듯 **애초에 필요 없는 장치**였다.

> 늘리는 제안은 "안 만들면 무엇이 깨지는가"를 함께 낸다. 안 깨지면 만들지 않는다.
> 검토는 결함을 **보고**하는 자리지 대응책을 **확정**하는 자리가 아니다.
> 심각한 문제는 **최소 3개 에이전트와 상의**한 뒤 **최종 판단은 사용자가 한다.**
> **`lead`도 예외가 아니다** — lead의 판정도 사용자 승인 전까지는 제안이다.

규칙은 별도 브랜치(`chore/agent-rules`)로 분리했다. 이 PR의 주제가 아니기 때문이다.
