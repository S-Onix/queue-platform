# Enqueue 경로 튜닝 실측

`BatchProcessor`의 상수 둘(`drain-interval-ms`, `capacity-cache-ttl-ms`)을 정한 근거다.
코드에는 결론과 포인터만 두고 실측표는 여기 둔다.

> 🪤 **전부 로컬(WSL2, 부하 도구가 서버와 같은 머신) 측정이다.** 절대값을 프로덕션에
> 옮기지 마라. 옮길 수 있는 것은 관계식과 함정뿐이다.
> 측정 절차는 `~/queue-platform-it/sweep.sh`·`burst.sh`(비커밋).

## 1. 드레인 주기 — 1000ms → 20ms (2026-08-27)

이 주기가 enqueue 응답 지연을 그대로 만든다. 요청은 Global Queue에 들어가 다음 틱을
기다리므로 **평균 대기가 주기의 절반, 최악이 주기 전체**다.

### ① 주기 스윕 (유입 100 RPS 고정, 큐 10개, 주기만 변수)

| 주기 | p50 | p95 | p99 | evalsha |
|---|---|---|---|---|
| 1000ms | 514.07ms | 965.09ms | 1000ms | 14,710 |
| 200ms | 119.08ms | 208.67ms | 211.23ms | 16,151 |
| 50ms | 40.80ms | 60.66ms | 61.51ms | 18,404 |
| 30ms | 28.77ms | 38.78ms | 39.78ms | 18,799 |
| **20ms** | 23.59ms | 25.86ms | **26.85ms** | 19,521 | ← 채택 |
| 10ms | 12.77ms | 23.29ms | 24.78ms | 19,465 |

- **왜 50ms가 아닌가** — 100 RPS에서도 p99 61.5ms로 이미 목표(50ms)를 못 넘는다.
- **왜 10ms가 아닌가** — 틱이 2배인데 비용이 포화해 이득이 없다(19,521 vs 19,465, 차이 0.29%는 노이즈).

### ② 유입별 (주기 20ms, 큐 40개, 초기화 1회 후 연속 측정)

| 유입 | 정순 p99 | 역순 p99 | FRS 목표(<50ms) |
|---|---|---|---|
| **200 rps** | 32.32ms | 29.21ms | ✓ ← FRS §13 목표 부하 |
| 500 rps | 30.77ms | 31.73ms | ✓ |
| 1,000 rps | 75.13ms | 37.07ms | ⚠️ 순서 의존 — 단정 불가 |
| 2,000 rps | 103.60ms | 81.06ms | ✗ 양쪽 다 초과 |

**목표 부하 200 rps에서 2.5배(500 rps)까지 견고하게 충족한다.**

🪤 **순서를 뒤집어 재라 — 안 그러면 워밍업을 부하로 착각한다.** 정순만 재고
"5배부터 초과"라고 결론냈다가 **철회했다.** 역순에서 1,000 rps가 토큰이 2배 더 쌓인
상태로도 37.07ms로 빨랐다. 누적 부하가 아니라 **JIT 워밍업**이다.

### ③ p99는 큐 수의 함수다 (2,000 RPS 고정, 큐 수만 변수, 429·503 0%)

| 큐 수 | p99 |
|---|---|
| 10 | 64.42ms |
| 20 | 77.37ms |
| 43 | 130.50ms |

틱당 그룹 수가 늘면 그룹마다 `getMaxCapacity`(DB) + `enqueue_bulk`(Lua)가 붙는다.
🔑 **"2,000 RPS에서 몇 ms"는 큐 수 없이는 의미가 없다.**

🪤 위 세 표는 **환경이 서로 달라 절대값을 섞으면 안 된다.** 각각 자기 조건 안에서만 읽어라.
(초기화까지 한 판이 따로 있으나 `enq_429`가 39.7%/7.3% 섞여 쓰지 않았다.
원인은 `plan=FREE`였고, **§88이 등급제를 걷어내 재발할 수 없다** — 한도가 전 테넌트 동일 상수다.)

### 프로덕션으로 옮길 것 — 숫자가 아니라 이 관계식

```
p99 ≈ 0.99 × 주기 + c        c = Lua + Kafka ack. 로컬 실측 7~19ms
evalsha_rate ≤ 유입 RPS      그룹핑이 항목 수보다 많은 Lua를 만들 수 없다
```

앞 식은 **큐 수·유입률과 무관**하다(틱 대기는 순전히 주기의 함수다).
뒤 식은 **구조에서 나오는 상한**이지 위 표가 근거가 아니다 — `evalsha` 합계에는
요청마다 도는 `token-bucket.lua`와 배치 잡이 섞여 있다(1000ms 판이 6,000요청에 14,710회).
**주기별 증가분 비교로만 읽어라.**

⚠️ `c`는 프로덕션에서 네트워크가 붙어 커지고, 큐 수가 늘면 p99가 함께 오른다.
되돌리기가 환경변수 한 줄이라 사전에 여유를 사지 않았다 —
**프로덕션에서 목표를 못 넘기면 10ms로 내려라.**

### 측정 함정

- 🪤 **워밍업을 빼지 마라.** 재기동 직후 바로 재서 콜드 스타트에 오염된 적이 있다.
  같은 조건에서 **577ms → 61ms(9배)**로 갈렸고, 그 값으로 "구조적으로 달성 불가"라는
  **틀린 판정**을 냈다.
- 🪤 **버스트는 주기를 고정해서 재라.** `burst.sh`가 주기를 지정하지 않아 직전 스윕이 남긴
  20ms 위에서 돌고는 "30ms 고정"이라고 보고했다
  (`burst_100` 25.76ms ≈ `sweep_20` 26.85ms ≠ `sweep_30` 39.78ms). 지금은 `MS=`를 필수로 요구한다.
- ✅ **`max` 2.2~2.6s는 서버 사건이 아니다**(2026-08-27 해소). k6 `http_req_duration` max가
  같은 판의 `iteration_duration` max를 **넘는다** — iteration이 요청을 포함하므로 산술적으로
  불가능하다. 서버 히스토그램에도 333,002건 중 1초 초과 0건. **측정 산물이다.**

## 2. `maxCapacity` 캐시 TTL — 30초 (2026-09-02)

### A/B 실측 (큐 20개, 총 2,000 rps, 각 4판)

| | p99 | 평균 | 판정 |
|---|---|---|---|
| OFF | 54.33 / 113.63 / 60.21 / 67.64 ms | 73.95 | 4판 전부 SLO(50ms) 초과 |
| **ON** | 39.87 / 39.61 / 40.14 / 40.47 ms | **40.02** | 4판 전부 충족 |

🔑 **가장 큰 신호는 평균이 아니라 분산이다.** 판 간 폭이 **60ms → 0.9ms**로 붙었다.
비용의 정체는 틱 50회/s × 큐 N개 = **초당 50N SELECT**다.
큐 8개(400/s)는 견디는데 큐 20개(1,000/s)에서 무너진다.

### 왜 TTL이 필요한가 — "불변"이 틀렸기 때문이다

처음엔 만료를 두지 않았다. `Queue.update()`가 `name`만 바꾸고 용량 변경 API가 없어
실질 불변이라고 봤는데, 🔴 **코드만 전수하고 런북을 안 봤다.** 장애 대응 문서가 직접
SQL 경로를 지시하고 있었다.

```sql
UPDATE queues SET max_capacity = <새값> WHERE queue_id = 'q_xxx';
```

만료가 없으면 `Q005 QUEUE_FULL` 장애 중에 운영자가 이 UPDATE를 쳐도 **아무 일도 일어나지
않고**, 회복 수단이 전 인스턴스 재기동뿐이다. 장애 중에 칠 수 없는 카드다.

### 왜 30초인가

근거는 **비용이 아니라 장애 대응 반응 시간**이다. 비용은 어느 값이든 무시할 만하다 —
큐 20개 기준 초당 1,000회가 **0.67회**가 된다(1,500배 감소).

🔑 **왜 5초가 아닌가** — 장애 반응만 보면 짧을수록 낫다. 30초를 지지하는 유일한 근거가
**큐 개수 상한이 없다**는 것이다. 큐 1만 개면 5초는 초당 2,000 SELECT로 원래 문제로
돌아간다. ⚠️ **비용이 `큐 수 ÷ TTL`이므로 큐 개수 상한이 정해지면 다시 잡아라.**

🪤 **인스턴스마다 만료 시점이 다르다.** 캐시가 JVM 안에 있어 N대가 각자 다른 순간에 다시
읽는다. UPDATE 후 30초 창 동안 인스턴스마다 판정이 갈린다 — 429가 줄다 사라지는 모양이고
30초 안에 수렴한다.

🪤 **이 실측 덕에 안 만든 것이 둘이다**(§4): 큐 단위 병렬 드레인(구조 변경)과
Redis 마스터 증설(인프라). 캐시 하나로 SLO를 지키므로 지금 둘 다 필요 없다.
