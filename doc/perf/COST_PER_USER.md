# 한 사람이 드는 비용 — Redis · MySQL · Kafka

> README 에서 옮겼다(2026-09-25). 원본: `~/resume-evidence/06_cost-local-20260924/`

> 📏 로컬 실측(2026-09-24, 큐 1개에 20,000명 → 3,000명 입장 → 절반은 verify · 절반은 complete).
> **바이트는 키 구조로 정해져 로컬에서도 유효하다.** 시간은 한 대에 다 올린 로컬 값이라
> **절대치보다 비율**을 봐라 — 성능의 정본은 [README](../../README.md) 의 AWS 표다.

**Redis — 1명이 단계마다 차지하는 메모리** (`MEMORY USAGE` ÷ 인원)

| 단계 | 생기는 것 | 1명당 | 언제 사라지나 |
|---|---|---|---|
| 줄 섬 | 대기 순번(`waiting`) + 명부(`tokens`) | 139 + 149 = **288 B** | 입장 시 순번만 빠진다 |
| 내 차례 묻기 | 생존 신호(`last-active`) + 요청 한도 버킷 | 97 + 168 B | 이탈 회수 · 버킷은 TTL |
| 입장권 받음 | 입장 목록 + 입장권↔토큰 양방향 키 | 136 + 280 + 216 B | 60초 |
| 〃 | 같은 요청 재시도용 응답 보관(`admit-idem`) | **164 B** (1회 300명 = 49 KB) | 5분 |
| 완료 | 명부·입장 목록·토큰 키 삭제 | — | verify는 입장권 키를 60초 남긴다(소비하지 않는다) |

입장권을 받은 순간이 최대이고 **1명 ≈ 1.2 KB**, 줄만 서 있을 땐 **288 B**다(100만 명 ≈ 288 MB).
구조별 합과 마스터 `used_memory` 증가분이 **4% 안에서** 맞았다. AWS 12차(254 B/명)와도 같은 자릿수다.

🔑 **입장권 1장보다 "같은 요청 재시도" 보관이 더 오래 산다.** 응답 전체를 5분 보관하므로
한 번에 300명씩 들이면 **호출마다 49 KB**가 쌓인다. 줄 선 사람 수가 아니라 **입장 속도**에 비례하는 비용이다.

**MySQL — 쿼리 1회 시간** (`performance_schema`, 평균 / p95)

| 경로 | 쿼리 | 평균 | p95 |
|---|---|---|---|
| 줄 섬 → 원장 적재 | 다중행 INSERT (문장당 평균 14행) | 1.31 ms (**행당 0.09 ms**) | — |
| 입장·완료 → 원장 반영 | 상태 전이 UPSERT | 3.26 ms (이벤트당 0.19 ms) | — |
| complete | 완료 표시 UPDATE | 1.05 ms | 1.9 ms |
| complete | 토큰 단건 조회 | 0.62 ms | 1.2 ms |
| verify (Redis에 없을 때) | 입장권으로 조회 | 0.75 ms | 1.5 ms |
| 거의 모든 요청 | 큐 조회 | 0.28 ms | 0.6 ms |
| — | **COMMIT** | **13.6 ms** | **38 ms** |

🔑 **쿼리는 전부 1ms 안팎이고 시간은 COMMIT이 먹는다** — DB 시간의 **77%**가 COMMIT(디스크 동기화)였다.
AWS 12차에서 병목이 COMMIT으로 옮겨간 것과 같은 모양이다. 줄이려면 쿼리가 아니라 **커밋 횟수**를 줄여야 한다.
> 📏 verify 폴백 0.75 ms는 인덱스를 넣은 뒤의 값이다. 넣기 전 AWS에서는 **198 ms**였다(README 성능 개선 ③).
> ⚠️ p95는 MySQL 기동 뒤 누적값이다(평균은 이 판만 떼어 계산했다). 로컬 COMMIT은 WSL 디스크라 AWS보다 느리다.

**Kafka — 발행에서 원장 반영까지** (`queue_consumer_apply_delay_seconds`, 26,000건 = 줄 섬 20,000 · 입장 3,000 · 완료 3,000)

| ≤ 50 ms | ≤ 100 ms | ≤ 500 ms | 최대 | 평균 |
|---|---|---|---|---|
| 70% | 88% | 99.86% | ≤ 5 s | 68 ms |

🔑 **이 지표가 생기기 전에는 "밀린 건수"만 볼 수 있었다.** AWS 13차에서 밀린 건수가 최대 33.5만이었는데,
그게 **몇 초 늦은 것인지는 답할 수 없었다.** 이게 중요한 이유는 입장 확인이 Redis에서 빠지면 원장으로
넘어가고, 원장 쪽 60초 창은 **반영된 시각부터** 잰다는 데 있다. 반영이 늦으면 그만큼 창이 밀린다.
> ⚠️ 발행한 서버와 반영한 서버의 시계 차가 그대로 섞인다. 시계가 거꾸로면(음수) 기록하지 않는다.
