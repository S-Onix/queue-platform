# 컨슈머 타입별 그룹 적재 — 커밋 절감 실측

대상: `TokenLifecycleConsumer.consume` (그룹 경로 vs 구간 분할 경로)
측정: 2026-08-27, 반사실 `splitTx`를 직접 세어 비교. 전 구간 32만 이벤트.

## 결과

| 파티션당 유입 | 배치 크기 | 커밋 절감 |
|---|---|---|
| 105~113건/s | 73~158건 | 84~96% |
| 2~3건/s | 5~10건 | **0%** |

전체 합계: 커밋 **76,806 → 13,080 (절감 83.0%)**. 두 판 재현(83.0% / 82.8%).

## 🔑 이득은 파티션당 유입률의 함수다

파티션당 유입이 낮으면 한 배치에 타입이 한 종류뿐이라 분할 경로도 트랜잭션을 하나만
연다 — 줄일 것이 없다. 손익 경계는 대략 **파티션당 50건/s**다.

🪤 **저부하 벤치로 "효과 없다"고 판단해 지우지 말 것.** 위 0% 구간이 정상이다.
되돌리려면 파티션당 50건/s 이상을 걸고 `splitTx`/`tx`를 다시 재라.

🪤 **재려면 반드시 `consume`의 debug 로그를 INFO로 올려라.** 2026-08-27 첫 판은 그 줄이
debug라 0건이 찍혀 커밋 수를 `ReplicationRoutingDataSource` 로그로 **유도**했고, 그 유도값
(2.33)이 실측(18.5)과 8배 어긋나 판정이 하루 밀렸다.
```
--logging.level.com.sonix.queue.consumer.token=DEBUG
```

🪤 **부하 도구가 서버를 굶기면 안 된다.** 하니스가 죽은 판은 유입이 파티션당 10건/s까지
눌려 절감이 0으로 보였다 — 코드가 아니라 측정이 틀린 것이었다.

## 중복 `tokenId` 빈도

그룹 경로의 전제(한 배치에 같은 `tokenId`가 두 번 없을 것)가 깨지는 비율:
**배치 9,443개 중 2개 (0.02%)**. 나머지는 전부 그룹 경로를 탄다.
